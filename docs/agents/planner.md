# planner —— 行程编排者

> 本文是 [架构说明](../architecture.md) 的展开：`planner` 的角色、边界与产出契约。

## 1. 角色

把素材变成行程的人。全队唯一**没有工具**的 LLM agent——这是刻意的。

划界判据在这里是**信息视野**：`planner` 的信息源就该只有 `researcher` 说出来的素材。给它联网，它就会绕过 `researcher` 自己查，那 `researcher` 白设了。

## 2. 工作场景

业务场景：拿到「北京出发、成都三天、两人、4000」这个需求，排出一份逐日行程。

**群聊位置**：`RoundRobinGroupChat` 的第二个说话人，由 `researcher` 的素材清单激活。

**实际看得到**：`user` 的原始需求 + `researcher` 的完整素材清单 + 此前所有消息（包括 `critic` 上一轮挑出的问题）。

**产出交给谁**：`critic` 逐条审；用户最终读到的就是它的表。

**它看不到什么**：网页原文。它只有 `researcher` 摘出来的那一行。这是设计不是缺陷——正因为看不到原文，它才没有能力「顺手编一个更便宜的酒店」。

## 3. 目标

一份无冲突、不绕路、不超预算的逐日行程。

三个「无」正好对应 `critic` 的三条硬检查（时间冲突 / 地理绕路 / 预算超支），第四条幻觉检查则要求它**只用素材里有的东西**。

换句话说：`planner` 的目标不是「排得好看」，是「排得经得起审」。

## 4. 能力

**权力**：无工具。这一节之所以还叫「能力」，是因为「没有工具」在这里是一种正向能力——它保证 `planner` 的全部信息都来自 `researcher`，从而让 `critic` 的幻觉比对有唯一基准。

**信息视野**：群聊全部消息。素材、用户约束、`critic` 历次问题，都在里面。

**盲区**：

- **不能联网补查**。素材里缺的东西，它只能标「待确认」，不能自己去搜。
- **不能验证素材真假**。`researcher` 搜回一个错价，它照抄，`critic` 也查不出来（见 docs/architecture.md 第 8 节）。
- **不做预算判断**。见 §5。

## 5. 职责

| 该做 | 不该做 |
|---|---|
| 按地理位置聚类，同一天的活动尽量在相邻区域 | 把景点按名气排，让用户一天横穿两次城 |
| 标注每项的耗时和花费，花费与素材一致 | 心算下「是否超支」的结论 |
| 素材里没有的写「待确认」 | 编造素材里没有的景点或价格 |
| 直接输出表格 | 复述素材原文 |
| 收到 `critic` 的问题后重排 | 跟 `critic` 争论「这样也行」 |

**「不该做」第二条是本项目最反直觉的一条**：`planner` 要**列出**各项花费和合计（`critic` 需要这些数字来复核），但**不下超支结论**。判断权归 `critic`——因为计算器只挂在 `critic` 身上，而算钱是 LLM 最容易翻车的地方。`planner` 一旦自己下了结论，`critic` 就有一半的可能会顺着它说「确实超了」，而不是自己算一遍。

## 6. 工具

**无。**

AutoGen 里的写法就是**不传 `tools=`**：

```python
planner = AssistantAgent(name="planner", system_message=..., model_client=model)
```

**为什么一把都不挂**：见 §1，且这条比 `researcher` 那条更硬——`researcher` 是「只给它一把」，`planner` 是「一把都不给」。任何「给它加个计算器会更准」的念头，都会同时废掉 `critic` 的立身之本。

## 7. 工作流程

1. 读群聊里的素材清单，抽出所有【景点】条目及其价格、位置
2. 读 `user` 需求，确认天数、人数、预算
3. **按地理位置聚类**。以成都为例：北郊（大熊猫基地）、西郊（都江堰）、市中心（春熙路、宽窄巷子）、西南（武侯祠、锦里）——把相邻区域的活动压进同一天
4. 排时段：每天上午/下午/晚间各安排什么，标注耗时
5. 列花费：逐项照抄素材里的价格 × 人数，末尾给合计行
6. 出表，交回群聊
7. （后续轮次）读到 `critic` 的问题清单 → **只改被指出的部分** → 重新出表。不要重发未改动的段落

## 8. 输出格式

本节给两个代码块——**角色 prompt** 与**格式契约**——以及拼接公式。拼起来就是可直接贴进 `persona.py` 的完整 `system_message`。

```
最终 system_message = 角色 prompt + "\n\n" + 格式契约
```

### 8.1 角色 prompt

```
你是「行程编排者」。用中文工作。你没有搜索工具，信息源只有资料员给出的素材清单，
以及用户拍板时说的话。

你的任务：把素材编成逐日行程。

硬要求：
- 按地理位置聚类：同一天的活动尽量在相邻区域，避免来回跑
- 标注每项的耗时和花费。花费必须与素材或用户拍板一致，不许改动数字
- 用户已经拍板的档位和金额本身就是合法数字，直接拿来填花费列，注明「用户拍板」。
  别因为素材里查不到就退回「待确认」——用户定了就是定了
- 素材里没有、用户也没定的信息不要编，宁可写「待确认」
- 列出各项花费和合计，但不要下「是否超预算」的结论——那是审查员的判断
- 直接输出行程表，不要复述素材原文，不要客套
```

### 8.2 格式契约

```
输出格式：一张 Markdown 表格，列固定为
| Day | 时段 | 项目 | 花费 | 备注 |

- 一天一行到若干行，按时段顺序排列
- 花费写数字；人数相关项按总人数计（如「门票 110（2人）」）
- 花费列在这两种情况下写数字：素材里的数字能直接算成这一项的总额，或者用户已经拍板
  了这一项。素材只有区间、外币，或者只有按公里/按小时计的费率而你不知道用量的，才写
  「待确认」，把原文放进备注。别让备注写「无来源」而花费列却杵着一个实数
- 用用户拍板的数字时，备注写明口径和「用户拍板」，如「250/晚 × 2 晚，用户拍板」
- 表格下一行写合计：合计：XXXX 元
- 没有的信息写「待确认」，不要留空
- 每轮都输出完整表（三个 Day 全写），不要只输出改动的那一天

不要写行程亮点，不要写总结陈词，不要评论审查员的意见。
```

**「花费列只在有素材数字时才写数字」为什么单列一条**：原契约只说了「没有的信息写
待确认」，实测 planner 会钻空子——备注写「无来源，待确认」，花费列却填一个实数
（如 `200/晚`）。这会**同时骗过 critic 的两条检查**：加总把它算进去，幻觉比对又因为
备注自认「无来源」而放它过关。一句话绕过两道关卡，必须点名堵。

**后来又补了「按公里计的费率」这一种**：`researcher` 的交出契约改成照抄费率原文后
（见 [researcher.md](researcher.md) §8.2），市内交通那格会拿到「起步价 10 元 / 3 公里」
这类**是数字、但算不出总额**的素材——按公里计价却没有里程数。如果只按「素材里有没有
数字」判断，它就会像门票一样被乘出来一个假总额。判据因此收紧成「**能不能直接算成
这一项的总额**」：门票 × 人数可以，费率 × 未知里程不可以。后者的正确出路是备注抄费率、
花费写待确认。

**`researcher` 后来多了 `taxi_fare`，但这条判据不变。** 它现在能给出具体路线的总额
（「诸暨站→五泄 27.1 公里，打车约 71 元」），`planner` 拿到这种素材照样可以写进花费列——
因为那是**素材里的数**，不是自己乘的。变的只是「有没有素材」，不是「允不允许折算」：
按公里计的费率、而手上没有那条路线的金额时，仍然只能写待确认。别把这个工具当成
「现在可以自己估打车了」的许可。

**「用户拍板」是第三类合法来源，这一条是被实跑逼出来的。** 有一轮的真实输出长这样——
用户已经拍板「住宿砍到 250 一晚」，行程表里住宿那行却仍然写「待确认」，`critic` 于是
报了一条：

> 住宿行仍为「待确认」……用户已选定「高层连锁 200-300 元/晚」，但住宿项金额仍写
> 「待确认」……改法：确定具体订哪家、哪两晚、每晚多少元，再回填住宿行金额。

`critic` 是对的——**用户都定了，为什么还是待确认？** 卡住的原因是契约只认「素材里的
数字」，而用户的话不算素材。于是用户拍板的 250/晚填不进去，`planner` 只能退回待确认，
`critic` 再报一次，这个回路空转。

**这和「日均 50」那类编造有本质区别**（见 [researcher.md](researcher.md) §8.2）：编造的
数字**没有来源**；而「250/晚」的来源是 `user` 在 handoff 时说的话，全群可见、可追溯，
`critic` 能拿它做比对。当初为了堵编造，把这两类一起禁掉了，**禁过头了**。现在花费列
认两条来源：素材里能算成总额的数字，或用户已拍板的数字，后者备注注明「用户拍板」。

**判据没松：** 「素材里查不到」仍然不等于「可以自己估」。松的是「用户已经给出数字」
这一种——它本来就不是估算，是约束。

**为什么是「每轮输出完整表」而不是「只输出改动的 Day」**：后者是我最初写下的，动机
是省 token，但那是个**过早优化**——docs/architecture.md 第 8 节明确告诫「不做优化，先接受」，
因为「过早优化会让『跑不对』和『省 token』两个问题缠在一起，没法 debug」。实测正是
如此：critic 反复报「表不完整」「口径不明」，而我分不清是 planner 没写好还是契约逼的。

更硬的一条理由是**critic 根本没法用片段干活**。它的四条检查里三条在数学上就需要整表：
「同一时段两件事」要跨行比 `Day`+`时段` 的重复值，「地理绕路」要看同一天全部项目，
「预算超支」要把 `花费` 整列加起来。只给片段，它只能靠记忆拼——**而记忆拼接正是幻觉的温床**。

**这个格式为什么必须固定**：列名固定，`critic` 才能逐条比对——「同一时段两件事」是查 `Day` + `时段` 两列的重复值；「地理绕路」是查同一 `Day` 内各 `项目` 的位置；「预算超支」是把 `花费` 列加起来跟用户预算比。列名一飘，`critic` 就得先猜这张表长什么样，那一步就开始产生幻觉了。

**`合计` 行的作用**：它是给 `critic` 的输入，不是给用户的结论。`planner` 提供数字，`critic` 提供判断。
