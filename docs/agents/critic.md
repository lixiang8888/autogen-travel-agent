# critic —— 审查员

> 本文是 [BUILD.md](../../BUILD.md) §四个 Agent 的展开：`critic` 的角色、边界与产出契约。

## 1. 角色

全队唯一持对抗立场的人，也是唯一挂计算器的人。它存在的全部价值是**在用户看到之前把错挡下来**。

BUILD.md 的判据：`critic` 与另外两个的区别是工具集（唯一有 `calculator`）+ 信息视野（必须同时看到 `researcher` 的原始素材**和** `planner` 的行程表）。三个 agent 里只有它需要「两份东西对着看」。

**判断它是否在工作的唯一标准**：它挑出的是不是**具体的、可验证的、带数字的**问题。只会说「行程安排合理，考虑周到」的 `critic` 等于多烧一份钱（BUILD.md 已知坑 4）。

## 2. 工作场景

业务场景：`planner` 出了一版成都三日行程，`critic` 负责找出它哪里会出问题。

**群聊位置**：`RoundRobinGroupChat` 的第三个说话人，由 `planner` 的行程表激活。

**实际看得到**：群聊全部消息——**尤其是 `researcher` 的原始素材**。这一点是它的命脉：幻觉比对需要基准，基准就是素材清单。如果它只看到 `planner` 的表，就只能对表本身泛泛而谈，退化成附和机器。

**产出交给谁**：三条路。

| 情况 | 输出 | 后果 |
|---|---|---|
| 发现客观错误（冲突 / 绕路 / 超预算 / 幻觉） | 问题清单 | 下一轮 `planner` 重排 |
| 客观检查全过 | `APPROVED` | 触发 `TextMentionTermination`，对话正常收工 |
| 遇到**主观取舍**（怎么修没有正确答案） | handoff 给 `user` | 触发 `HandoffTermination`，team 停下等用户拍板 |

**它的输出是流程的开关**：整个群聊能不能停下来、以哪种方式停下，取决于它。

## 3. 目标

交付给用户之前，挡下四类硬错误：

1. **时间冲突**——同一时段安排了两件事
2. **地理绕路**——同一天跨区来回跑
3. **预算超支**——各项花费加总是否超过用户预算
4. **幻觉**——行程里的景点和价格，是否在 `researcher` 的素材清单里出现过

第 4 条是杀手锏，也是唯一一条它必须依赖别人输出才能做的检查。

## 4. 能力

**权力**：唯一持有 `calculator`；唯一的对抗立场（可以否定 `planner` 的产出）。

**信息视野**：群聊全部消息，特别是 `researcher` 的素材原文。它是唯一一个「需要两份东西对着看」的 agent。

**盲区**（两条，都是能力边界不是 bug）：

- **只能比对「素材里有没有」，不能判断「素材本身对不对」**。`researcher` 搜回一个错价，`critic` 会认为它是真的（BUILD.md 已知坑 6）。所以最终把关的是用户，来源链接是给用户点的。
- **不能改行程**。它只指出问题，重排是 `planner` 的活。它一旦自己开始改，就同时失去了对抗立场——变成自己审自己。

## 5. 职责

| 该做 | 不该做 |
|---|---|
| 钱必须用 `calculator` 算，不许心算 | 说「行程不错」「考虑周到」这类零信息量的话 |
| 每条问题说清：是哪一条、差多少、该怎么改 | 有问题时输出 `APPROVED` |
| 对照素材逐条查幻觉 | 改行程（只指问题） |
| 所有问题解决后才输出 `APPROVED` | 把 `APPROVED` 和其它内容混在一起输出 |
| 挑不出问题时先自查是不是没看到素材 | 因为「大体没问题」就放行 |
| 遇到主观取舍时触发 handoff 交回用户 | 替用户做主观取舍（改预算、砍景点） |

**「客观错误」和「主观取舍」的分界**——这是本 agent 最难的一条判断，判错会让流程要么卡住、要么越权：

- **客观错误** → 自己出问题清单。有唯一正确答案：「同一时段两件事」是错的，不需要问任何人。
- **主观取舍** → handoff 给 `user`。没有正确答案，只有偏好：「预算超 570，砍住宿还是改交通」，`critic` 无论选哪个都是**替用户做决定**。

判据是问自己一句：**这个修改的取舍，我有没有资格替用户做？** 没有就 handoff，不要自己拍板，也不要把问题丢回 `planner` 让它瞎猜（它会随便选一个，然后你又得审一轮）。

**`APPROVED` 的硬约束**：`TextMentionTermination` 是**按子串匹配**的，不是按整条消息匹配。写成「尚未 APPROVED」或「APPROVED 之前还需要……」会**误触发终止**，对话在一堆问题没解决时就停了。所以它必须裸着、独占一行、不与任何其它内容同现。

同时，只有所有问题都解决才输出它——否则它会在一堆问题没解决时就客气地说「基本没问题，APPROVED」（BUILD.md §终止条件）。

## 6. 工具

**`calculator`**（全队唯一挂载者）

| 项 | 契约 |
|---|---|
| 入参 | 一个算式字符串，如 `"750*2*2 + 350*3"` |
| 返回 | 数值结果 |
| 用途 | 所有加总、乘人数、比预算的运算 |
| 算不出时 | 说明是哪个数缺了（「住宿价格待确认，无法加总」），不要拿估计值凑 |
| 绝不允许 | 心算。哪怕是一眼能看出的加法 |

**为什么计算器必须挂在它身上**：算钱是 LLM 最容易翻车的地方，而这个 agent 的立身之本就是抓错。让它心算等于自废武功。

**`handoffs`**（声明一条通向 `user` 的通道。它不是工具，但同样挂在 agent 上，且同样依赖 function calling）

```python
from autogen_agentchat.base import Handoff

critic = AssistantAgent(
    name="critic",
    system_message=...,          # 8.1 + 8.2 拼接
    model_client=model,
    tools=[calculator],
    handoffs=[Handoff(target="user", message="需要用户拍板")],
)
```

| 项 | 契约 |
|---|---|
| 触发方式 | 模型生成一次工具调用，产生 `HandoffMessage(target="user")` |
| 效果 | `HandoffTermination(target="user")` 命中，**整个 team 停下**，控制权交回用户 |
| 前提 | 模型必须支持 function calling（BUILD.md 的 `model_info` 已开，这条不能省） |
| 何时用 | **只**用于「客观错误 / 主观取舍」里的后者，见 §5 |
| 续跑 | 用户回复后会以 `HandoffMessage(source="user", target="critic")` 交回给它，见 [user.md](user.md) §7 |

**为什么它需要这条通道**：它的四条检查都是客观的，但**怎么修**往往主观——「预算超了 570，砍住宿还是改交通」没有正确答案，只有用户的偏好。没有这条通道时只有两个坏选择：要么 `critic` 自己替用户决定（越权），要么让 `user` 卡在轮转里阻塞整个 team（见 [user.md](user.md) §2.1）。

## 7. 工作流程

1. 从群聊里**先取 `researcher` 的素材清单**，取不到不开始审——它没有基准
2. 逐条过 `planner` 表里的每个项目，回查素材清单：这个景点在吗？这个价格对得上吗？→ 抓幻觉
3. 查同一 `Day` 内 `时段` 列有无重复值 → 抓时间冲突
4. 查同一 `Day` 内各 `项目` 的地理方向有无来回穿城 → 抓绕路
5. 把 `花费` 列丢给 `calculator` 加总，与用户预算比 → 抓超支
6. 有问题时**先分类**：
   - **改法唯一**（如同一时段撞了两件事，挪走一件就行）→ 输出问题清单，本轮结束，等 `planner` 重排
   - **改法有多种、各有代价**（如超预算，砍住宿还是改交通）→ **触发 handoff 交回用户**，不要自己选
7. 客观检查全过：输出裸的 `APPROVED`
8. 若第 2–5 步一条都没挑出来，**先怀疑自己是不是没看到素材**，而不是宣布行程完美

## 8. 输出格式

本节给两个代码块——**角色 prompt** 与**格式契约**——以及拼接公式。拼起来就是可直接贴进 `persona.py` 的完整 `system_message`。

```
最终 system_message = 角色 prompt + "\n\n" + 格式契约
```

### 8.1 角色 prompt

```
你是「审查员」，负责在行程交付给用户之前挑错。用中文工作。

对行程表逐条检查四件事：
1. 时间冲突——同一时段安排了两件事
2. 地理绕路——同一天跨区来回跑
3. 预算超支——各项花费加总是否超过用户预算
4. 幻觉——行程里的景点和价格，是否在资料员的素材清单里出现过

硬要求：
- 算钱必须用 calculator 工具，不许心算
- 只对照资料员的原始素材做幻觉比对，不要凭自己的记忆判断景点是否存在
- 说问题要具体：是哪一条、差多少、该怎么改
- 如果问题的改法需要用户在多个方案间取舍（预算砍哪里、放弃哪个景点），
  调用 handoff 工具交回用户，不要自己决定
- 不要评论行程的风格、亮点、舒适度
- 只有在所有问题都已解决时才输出 APPROVED
```

### 8.2 格式契约

```
输出格式：

有问题时：
问题 N 条：
1. <问题类型>。<具体到哪一天哪一项>，<数字>。<建议改法>。
2. ...

无问题时：只输出一行，内容为
APPROVED

该行必须只有 APPROVED 这八个字符，前后不加标点、空格或其它文字。

不要写「整体不错」「考虑周到」这类评价，不要写结语。
```

**这个格式为什么必须固定**：输出格式就是流程的开关。`APPROVED` 一旦和别的字混在一起，要么误停（子串匹配到半截的终止词），要么永不停（漏掉终止词，撞上 15 轮上限）。问题清单的编号结构则是给 `planner` 读的——它要能逐条对上改。

### 8.3 提示词反模式

本节记录**不该往 prompt 里写什么**。第一条是本文踩过并改掉的。

**反模式 1 ★★★ · 在 prompt 里写「不要输出 X」**

8.2 的第一版曾在格式契约里写：

> 注意：APPROVED 必须裸着独占一行，不要写成「尚未 APPROVED」或「APPROVED 之前还需……」

两个理由说明这是自伤：

1. **否定式指令把禁用词送进了上下文**。加上这行后，`APPROVED` 在系统提示里从出现 1 次变成 4 次，还附带两种错误拼法。模型复述刚看到的字符串的倾向，远强于服从一个否定副词。
2. **它把「怎么错」教给了模型**。「APPROVED 之前还需……」这种半截话，模型本来想不到——是这行提示词写出来的。

**改法**：只写正面要求（「该行必须只有 APPROVED 这八个字符」）。错误长什么样，写在说明书正文里给人看，不写进 prompt。

**反模式 2 ★★ · 在 prompt 里复述别人的产出格式**

`planner` 的契约如果写成「像资料员那样列出价格」，模型会去模仿素材清单的行格式，而不是排表。格式契约只描述**自己要输出的东西**。

**反模式 3 ★ · 用「尽量」「原则上」软化硬约束**

`critic` 的退出条件是二值的（有问题 / 没问题），没有中间态。「尽量挑出真问题」会给它台阶下，退化成 BUILD.md 已知坑 4 的附和人。

**与「口吻禁令」的边界**：8.1 和 8.2 里到处是「不要复述」「不要客套」这类否定句，看着跟反模式 1 冲突。区别在**失效后果**：

- **口吻类禁令失效** → 多烧 token，流程还能跑。用禁令是收益大于风险的选择（BUILD.md 已知坑 3 的对策）。
- **退出词类禁令失效** → **流程崩**（误停或永不停）。这类只能写正面要求，一个反例都不许举。

⚠️ 反模式 2、3 是按同一原理**预判**的，尚未实测。跑起来后若发现反例，回本节更正。
